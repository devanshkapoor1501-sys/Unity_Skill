0028: 1. Executive decision
0029: 1.1 The corrected mission
0030: PolyForge should help Codex and compatible agents choose, understand, apply, combine, inspect and troubleshoot Blender and Unity tools for a user-specified task. It should supply just-in-time, version-aware technical instructions, tested capability implementations where useful, safe discovery for unfamiliar operations, and reliable evidence of what actually worked. The user may request a model, an animation, a scene modification, a shader, a controller, a diagnostic report or a game. PolyForge must not silently reinterpret those requests as a robot/arena/game-generation pipeline.
0031: The product consists of three existing layers: (1) a portable Agent Skill (.agents/skills/polyforge/SKILL.md and targeted references); (2) a local, largely model-independent Python CLI/capability engine with schemas, orchestration, security, inspection, benchmarks and provenance; (3) Blender Python and Unity C# Editor/runtime adapters. Existing Blender/Unity MCP integrations can complement it. A website, SaaS platform, new universal MCP server or retrained model is not required.
0032: Success means Codex handles varied, unfamiliar, appropriate Blender and Unity tool tasks correctly with lower friction or fewer errors than an equally equipped general agent, and truthfully reports unverified or unsupported operations. Success does not mean generating a complete game, mastering every API entry point, producing AAA art, permanently training Codex, or spawning genuine independent AI agents merely because roles have separate names.

0050: 1.3 Why the old plan needed revision
0051: The previous roadmap correctly preserved useful code, but it mixed tool competency with game production. Its game_manifest, GAME ACCEPTED, playable-game release gate and genre-wide benchmarks could all direct Codex toward building full demo games. Its five-task asset pilot could not measure broad tool knowledge, and old Phase 17 forced a choice of animation or gameplay even though neither should be excluded from knowledge coverage. The legacy appendices carried obsolete commands and expansive game requirements beside the new restricted mission. This document makes tasks and tool domains, not genres or game count, the unit of progress.
0052: 1.4 Non-negotiable preservation
0053: •  Do not delete or reimplement existing code simply because a former phase has been renamed. Preserve Python CLI, schemas, registry, Blender modeling/animation, Unity C# integration, 2D workflow, artifacts, tests, journals, recovery, Git history and benchmarks.
0054: •  Keep the robot arena, platformer and known scenes as frozen regression/integration fixtures, not templates every user request must use. A failing old fixture is a regression; passing an old fixture is not proof of generality.
0055: •  Existing project inspection must remain non-mutating. Native actions require an approved managed/disposable copy. Keep the Unity project-writer lock, path restrictions, subprocess ownership/timeouts, approvals and rollback checks.
0056: •  Distinguish an instruction in SKILL.md, a reference to an API, a successful probe, a registered tested operation and independent acceptance. None implies the others.
0057: •  Existing local sequential roles are not claimed to be independent concurrent AI agents. Actual host delegation needs observed evidence and permission isolation.

0149: 3.2 Bounded pilot charter (proposed numbers, not preapproved)
0150: Initial pilot workflow: A task from specification to editable Blender source → technical preview → FBX/LOD where applicable → managed Unity import → exact geometry, axis, socket and reference evidence. The benchmark measures whether PolyForge makes Codex better at that tool workflow; it does not claim competence across all other Blender/Unity domains.
0151: •  Proposed cap: 16 focused hours over 7 calendar days once the owner approves: up to 6 hours for Phase 12 defect/qualification and up to 10 hours for Phase 13 paired evaluation. Include debugging, trial setup and review in tracked time.
0152: •  Proposed trial: Five independently selected unseen paired tasks (10 attempts, two arms), varied in object geometry and coordinate transforms, with an independent technical acceptance rubric. Pre-register pass/fail, elapsed time, interventions and cost.
0153: •  Proposed positive gate: At least 4/5 PolyForge-assisted outputs accepted, zero undetected critical coordinate/socket defects, no lower accepted count than equal-tool Codex, plus ≥20% lower median end-to-end time OR ≥30% fewer manual corrections, provided quality is not reduced. These thresholds are provisional management choices, not statistical proof of universal superiority.
0154: •  Independent reuse: On calendar days 8–14, a fresh/reset operator repeats one approved task in a clean workspace. Proposed up to 1 additional preapproved hour; record install/setup, output, manual fixes and elapsed time. Missing repeat evidence = provisional result.
0155: •  Stop immediately on authorization expiry, cap/deadline overrun, unsafe original-project mutation, tool-parity failure, missing independent evaluator or critical unrecovered regression. Mark STOP / NARROW / CONTINUE / INCONCLUSIVE with written rationale. A successful pilot permits considering the next small workstream, not starting every remaining phase.
0156: 3.3 Important scope correction to the pilot
0157: One strong cross-engine asset trial is necessary but insufficient to establish the broader tool-competency mission. After a successful pilot, each prioritized Blender/Unity domain must run its own small independent positive, negative and transfer tasks. Report coverage per tool family and application version; do not manufacture an “overall mastery percentage” by counting knowledge cards or easy examples.
0158: 4. Canonical tool-competency model
0159: 4.1 Three separate questions for every tool family
0160: 1.  Knowledge: Can the skill identify appropriate tools/APIs, when to use them, prerequisites, the correct Blender/Unity version, expected context and common mistakes?
0161: 2.  Execution: Has Codex actually completed an operation using that tool in the declared environment, within safety limits, with useful output and reproducible evidence?
0162: 3.  Independent transfer: Can a separate evaluator verify a new/unseen variation, including a negative case, without relying on generator-authored expected results?
0163: Do not replace all three questions with one boolean supported=true. Skill references and tool descriptions are knowledge, not proof of working automation. Code existence is not proof native execution passed. Game-playability is irrelevant to a UV unwrap task, an Editor import probe or a shader graph inspection.

0194: 4.3 Canonical record for every competency
0195: Each domain/tool-family entry should include at least: id, application, domain, subfeature, intent_patterns, version_range_tested, api_symbols_or_editor_features, prerequisites, context_modes, supported_operations, known_unsupported, input_schema, result_schema, references_with_source_date, safe_probe, positive_test_ids, negative_test_ids, unseen_transfer_ids (access-controlled), metrics, human_review_needed, support_state, last_execution, evidence_paths, owner, expiry_or_revalidate_condition and risk_class.
0196: Knowledge cards must remain lightweight and lazily loaded. A router can choose relevant references; references must not be executable instructions with authority to expand filesystem/network privileges. All recommended operations should be linked to real supported capability IDs or explicitly labeled exploration paths.
0197: 4.4 Minimum behavior of the task-first router
0198: •  Preserve the original user request exactly. Classify the deliverable (EXPLAIN, INSPECT, CREATE_ASSET, EDIT_ASSET, ANIMATE, EDIT_SCENE, ADD_COMPONENT, FIX_PROJECT, TEST, EXPORT_IMPORT, BUILD_GAME only when explicitly requested). The presence of the word “robot” or “Unity” never authorizes a game build.
0199: •  Extract constraints: application versions, project path/ownership, artifact expectations, style/quality, target platform, available time, resource limits, accepted modifications, required visual review and success criteria.
0200: •  Consult tool version probes and available capability registry. Choose the smallest set of required tools and specialists. Do not run Unity when a Blender-only task is sufficient or generate meshes for an explanation-only request.
0201: •  Return a structured plan with supported, experimental, assisted and unsupported requirements, plus alternative approaches only if the user approves an amended scope. If a required piece cannot be implemented, remain PARTIAL or BLOCKED rather than substituting the arena fixture.
0202: •  Run tests appropriate to the specific tool operation. Preserve provenance and actionable errors; ask for approval before protected actions and stop on budget.
0203: 4.5 Safe unfamiliar-tool discovery
0204: For unknown Blender operators, node APIs, Unity Editor callbacks, packages or runtime components: (1) inspect official version-matched references; (2) confirm installed version and dependency availability; (3) inspect non-mutating API signatures and known context requirements; (4) build a disposable scratch case; (5) run a positive case, deliberate negative case and different-input transfer case; (6) inspect logs and output with a reviewer; (7) register a new validated capability only after approval and evidence. Keep unverified work EXPERIMENTAL/ASSISTED/BLOCKED. Never execute arbitrary scripts from web pages, prompts or asset metadata.
0205: This is procedural expertise, not model retraining. A skill can provide just-in-time knowledge and tested tools; it cannot make Codex permanently remember every function or guarantee creative/artistic quality.

0318: 6. Architecture, data contracts and worker policy
0319: 6.1 Functional layering
0320: User request → Host agent → PolyForge skill trigger → TaskIntent/knowledge router → Version probe and support map → Typed operation plan → Existing capability engine or approved scratch experiment → Blender/Unity adapters → Technical and independent review → Artifacts + evidence + truthful limitations.
0321: The host agent decides task intent and may write project-specific code. The skill provides decisions and references. The engine executes safe registered operations and maintains traceable state; it does not embed a model provider, own model credentials or dynamically execute untrusted code. Complex tasks may use multiple specialist roles, but the coordinator must minimize the graph and record actual execution mode.

0343: 6.3 Existing CLI contract and additions
0344: Keep canonical implemented syntax authoritative (polyforge capability list/show/run, knowledge list/route/probe, workforce roles/plan/run/status/review, doctor, build, audit, verify, inspect-project, benchmark). Any proposed competency list/show/verify/coverage, tool-task plan or task report command must first be checked for equivalent implemented functions, then added only with tested help/docs, schema and exit-code compatibility. Do not create shadow commands that disagree with polyforge/commands.py.
0345: Invocation status: PASS, FAIL, BLOCKED, NOT_RUN, REVIEW. Task outcome: ACCEPTED, PARTIAL, REJECTED under separately authored task-specific mandatory requirements. Competency state: Section 4.2. Artistic review: separate approval. Treat one native test PASS as proof only for that native operation, never universal Unity or Blender mastery.
0346: 6.4 Specialist roles should be tool-domain roles
0347: Keep existing Role-based workflow infrastructure and all safety controls. Retain coordinator, requirements analyst, Blender modeling/UV/shader/rig/animation specialists, Unity Editor/C#/physics/UI/render/test specialists, cross-engine importer, independent inspector, security/recovery reviewer and release supervisor as task-selected logical roles. A task should normally use the smallest helpful subset: Blender material-only → Shader Specialist + Inspector; Unity prefab → Editor Engineer + Inspector; cross-tool import → Blender Export + Unity Import + Coordinate QA. There is no mandatory “Game Director → Level Artist → Enemy Programmer → QA” pipeline.

A reviewer on the same host is independent of a producer's edit privileges only within enforced boundaries, not automatically an independent evaluation authority.

0577: 8.3 Benchmark methodology
0578: Compare at minimum C (general Codex with maintained Blender + Unity tools) against D (identical tools + PolyForge). A baseline may outperform PolyForge; report that result and narrow or retire the weaker capability.

0629: 9.1 Execution cycle for every approved work item
0630: 1.  Verify current Git HEAD and clean/dirty status; branch/tag before risky edits. Discover actual installed Blender/Unity versions and CLI command support.
0631: 2.  Read the authoritative v7 phase, impacted source modules and only relevant official versioned references. Older blueprints are archival; do not execute their overwritten game-generation instructions.
0632: 3.  Freeze a small task contract with its exact user benefit, capability domain, existing code reused, files proposed, risk, per-task acceptance, independent owner, budget and stop conditions.
0633: 4.  Run existing regressions and a deliberately failing red test for the defect/new operation. Reject a plan that merely writes a green test asserting its own implementation.
0634: 5.  Implement the smallest reversible code/schema/reference change. No duplicate framework and no arbitrary shell/network access from user content.
0635: 6.  Run lint/type/unit, native Blender or Unity tests only where relevant, positive/negative/mutation cases and required independent acceptance. Record actual commands, tool versions and logs.
0636: 7.  Inspect resulting files, source hash/provenance, visual evidence if applicable, original-project nonmutation and rollback. Separate same-host technical review from truly independent external acceptance.
0637: 8.  Produce phase report with all statuses PASS/FAIL/BLOCKED/REVIEW/NOT_RUN, limitations, actual costs, artifacts, diff, next permitted task and explicit no-go conditions.
0638: 9.  Commit after tests; push and inspect CI only when user has authorized repository changes. Do not claim a remote push or CI completion from local command output alone.
0639: 10.  Stop at the phase/submodule boundary, including budget. Do not begin unrelated capabilities merely to improve coverage numbers.
0640: 9.2 Correct handling of existing project files
0641: A read-only inventory may inspect package versions, GUIDs, script namespaces and files without launching Unity on the original. To test compatibility or generate edits, create an approved isolated copy; apply managed Unity API changes inside allowed paths; compute before/after inventories and preserve .meta GUID identity. Use native reimport/reconstruction for rollback; copying files without semantic verification is insufficient. Never delete, publish or overwrite unmanaged source automatically.
0642: 9.3 Resource, environment and version rules
0643: Python launcher and tool versions are probed, not presumed. The repository's current reported native baseline is Blender 5.2.2 and Unity 6000.6.3f1, but future runs must discover installed versions and mark compatibility accordingly; source text of v5.1 naming Blender 5.0 does not override actual runtime evidence. Use bounded CPU/memory/disk/GPU/render budgets and explicit process timeouts; unknown resource measurements do not count as PASS. Mark unsupported host-native parallelism or untested Mac/Linux as not verified. Do not claim exact byte-identical FBX or physics across platforms; compare bounded semantic invariants with declared tolerance.
