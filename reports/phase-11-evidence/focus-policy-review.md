# Phase 11 focus policy authority review

Read-only design/source review requested by the coordinator. No runtime or test source edits, test execution, native launch, UI calls, process manipulation, or performance measurement were performed. This report is the only authored artifact. Applied the code-review-and-quality skill to check the proposal against the written contract; existing constraints were read rather than redefined.

## Verdict

**The reviewed user authority does not require continuous foreground focus.** Approve the proposed explicit focus-tolerant measurement policy in principle, subject to the preservation and evidence conditions below. It is an observable relaxation of an implementation-added rejection rule and must be disclosed as such; it is not a reduction of a foreground requirement found in the blueprint or approved implementation plan. No new performance PASS follows from this review.

The proposal can measure the declared Windows standalone profile without quietly lowering its numeric or duration bar. It cannot support a claim of uninterrupted foreground performance or independent GPU/display presentation proof for every counted interval. Existing failed attempts stay FAIL; only a newly frozen and measured run group can be scored under the revised policy.

## Minimal honest policy

Declare, before rebuilding/recollecting, that focus changes are allowed, background execution is enabled, and focus is diagnostic evidence. Keep policy in the profile digest, request/runtime binding and reported profile so old/new measurement policies cannot be accidentally pooled. Update the design/report and replace the old focus-only rejection test with behavior tests for the new declared policy; do not silently delete it to get green.

Keep the existing single continuous measurement window per launch. Record every positive finite end-of-frame interval after warmup until the existing >=60-second endpoint. Do not pause timing, reset warmup, restart the window, omit an unfocused interval, splice windows, cap slow intervals or select replacement samples automatically. Keep all three independent launches and the current full-window/frame-sum, duration, overflow, scene/activity, resolution/quality/pacing, hardware/build/profile identity, process ownership/readiness, load/RSS and per-sample threshold checks. PC quality and 1280x720 must remain validated continuously as they are now. Failed attempts and partial evidence remain discoverable.

Record focused/unfocused measurement-frame counts whose sum equals `frames_recorded`, plus timestamped focus-change events and the initial observed focus state. Define whether counts classify each interval using focus at its closing callback; a transition can occur inside an interval, so these counts do not prove its entire duration had one state. Preserve callback events even when multiple occur between rendered-frame observations. Do not demand that callback-event count equal frame-sampled state transitions. A legacy aggregate `focused` field may remain diagnostic only with documented semantics, or be superseded explicitly; it must not falsely become true for mixed-focus runs. Report actual `runInBackground` as well as its declared setting.

If an unfocused or occluded window still produces callbacks, all those intervals enter the same statistics. If progress stops and later resumes, the full gap belongs to the next interval; if it never resumes, timeout/incomplete evidence remains a failure or disclosed environmental block, never PASS. The existing median/P95 gates do not guarantee that every isolated stall fails (a small tail can fall beyond P95); retain raw intervals and elapsed FPS and make no stronger claim. Adding a new minimum elapsed-FPS gate would be a separate contract change and is not required by this proposal.

Retain the current non-Editor, non-batch, non-nographics, non-Null-device, camera/binding and end-of-frame-path guards. They establish the declared instrumented render-loop context within the current evidence model. `SystemInfo.graphicsDeviceType` alone establishes device/API identity, not that a particular frame executed meaningful GPU work or reached the display. Focus also does not establish visibility, absence of occlusion, scanout, or GPU workload. Do not infer an uninterrupted-visible-window claim from focus counters or from a fast result. GPU utilization remains UNKNOWN unless measured separately. The proposal does not require inventing a stronger per-frame GPU proof absent from the written contract.

Missing draw-call/polygon/texture or other required metrics must remain explicitly NOT_RUN as required by §9.8; this focus correction does not cure those omissions or establish the overall release gate. Arena results remain a bounded verification fixture for the portable skill/tool engine and specialized workers, not proof of performance across arbitrary games or complete broad expertise.

2. Malformed/missing/noninteger/negative focus counts, count sums inconsistent with frame count, invalid focus-event state/timestamps and mismatched declared/reported background policy fail evidence validation rather than silently normalizing to a passing value. Frame omission/truncation, wrong frame sum, shortened/overlong duration, missing sample, bad process/resource evidence, frozen workload, Null device, batch and Editor fixtures continue to fail. Collect three fresh full samples on the same declared hardware with focus events/counts, raw intervals, per-sample durations, activity, actual quality/resolution/device/build and external RSS/load observations. ### Finding: diagnostic transition consistency

**P2 — `performance.py:104–116` accepts impossible closing-state transition counts.** It validates that focused/unfocused counts sum to `frames_recorded` and `focus_changes <= frames`, but a fixture with 3000 focused closing states, zero unfocused states and `focus_changes=3000` satisfies those predicates. The recorder can produce at most one transition for all-identical closing states (from a different measurement-start state to the first observation). Likewise mixed closing-state counts cannot have zero transitions. This is a source-derived deterministic counterexample, not an executed probe. It does not lower FPS/P95/RSS/load gates, but the reported validation claim that transition counts are consistent is too broad. Add a focused malformed-evidence regression and feasible-count bounds before claiming this diagnostic is validated. With the initial state unspecified, an achievable conservative upper bound is `min(frames, 2*min(focused_frames, unfocused_frames)+1)`; when both closing states occur, at least one transition is required. No new performance threshold is needed.

### Diagnostic scope adjustment

The implementation intentionally records a **sampled transition count**, not timestamped `OnApplicationFocus` events or the initial focus state. It expressly disclaims intervening events, so it does not misrepresent these counts as event telemetry. This is narrower than the earlier proposed event log and this review's suggested evidence list. No mandatory event-log requirement was found in the user authority; do not turn that recommendation into an invented release constraint. The coordinator can adopt this simpler diagnostic scope explicitly, provided reports call `focus_changes` sampled closing-state transitions and make no claim to capture every focus event. A real transition-path observation remains pending native verification; the pure Python fixtures and C# syntax parse do not prove actual Unity behavior.

**Re-review disposition:** focus policy correction is justified and continuous-collection logic is consistent with it. Address the narrow P2 diagnostic-count validation finding before claiming complete evidence validation. Fresh rebuilt three-sample native qualification and transition-path evidence remain pending; no native PASS is inferred.
